The 1.0 architecture keeps one build-time graph aligned across runtime layout
behavior, generated TypeScript types, and Nuxt Content schemas. The next
breaking release establishes that boundary before the API is declared stable.

## Keep Structure in the Registry

Every variant name and every `extends` relationship belongs in
`variants.registry` in `nuxt.config.ts` or an extended Nuxt layer.

```ts [variants.ts]
import { defineVariantRegistry } from "@happydesigns/nuxt-variants/schemas";

export const variantRegistry = defineVariantRegistry({
  header: {},
  toc: {},
  content: ["header", "toc"],
});
```

`defineVariantRegistry` is optional at runtime, but recommended for a shared
registry because it preserves literal names, parent tuples, and values without
adding another graph object.

## Keep Values in App Config

`app.config.ts` may override `config` and `active` for registered entries.

```ts [app.config.ts]
export default defineAppConfig({
  variants: {
    toc: {
      active: true,
      config: { title: "On this page" },
    },
  },
});
```

Move these patterns out of app config before upgrading:

- a variant name that is missing from the build-time registry;
- an `extends` property or array shorthand;
- any expectation that app config can change the generated graph.

Nuxt now fails startup with a structured `VariantRegistryError` for those
cases. The error reports all violations together.

## Review Public Types

Runtime config generics now require object shapes. This rejects primitive
configuration types that could never be merged safely. Use `VariantName` for
known registry names and `VariantNameInput` when an integration also accepts
dynamic route or CMS values.

## Verify Layers

Nuxt layers continue to contribute registry entries through normal Nuxt config
merging. The DevTools inspector shows every declaring layer in Nuxt precedence
order, which makes accidental shadowing visible without exposing local paths.
