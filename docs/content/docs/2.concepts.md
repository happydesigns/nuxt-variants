## Registry Entries

A registry entry describes one named config contribution.

```ts
type VariantDefinition<T> = {
  extends?: string | string[];
  active?: boolean;
  config?: Partial<T>;
};
```

An entry can be a small feature such as `header`, `toc`, `authors`,
`copyButton`, or `surround`. It can also be a page or collection variant such
as `article`, `event`, or `content`.

The registry is structural build-time configuration. It is the single source
of truth for known names and inheritance. `app.config.ts` is deliberately a
value layer: it can override `config` and `active` for a registered entry, but
cannot add names or define `extends`.

## Feature Composition

Variants compose features through `extends`.

```ts
registry: {
  authors: {},
  header: {},
  toc: {},
  copyButton: {
    config: { copyButton: { label: "Copy URL" } },
  },
  article: {
    extends: ["authors", "header", "toc", "copyButton"],
    config: {},
  },
}
```

`article` now exposes the four capabilities through `has()` and inherits the
copy-button configuration.

## Shorthand Extends

When a variant only extends other entries and has no own config, use an array.

```ts
registry: {
  content: ["header", "toc"],
}
```

This is equivalent to:

```ts
registry: {
  content: {
    extends: ["header", "toc"],
    config: {},
  },
}
```

## Merge Priority

When `useVariant("article")` resolves config, the final value priority is:

1. `app.config` for `article`
2. `nuxt.config` for `article`
3. the last parent in `extends`, with its own app config ahead of its base config
4. earlier parents in `extends`, each with the same app-before-base priority

Objects are deeply merged. Arrays are replaced, not concatenated.

## Inactive Variants

Set `active: false` when a registry entry should exist in the graph but not
contribute behavior.

```ts
registry: {
  draft: {
    active: false,
    extends: ["header"],
    config: {},
  },
}
```

`useVariant("draft").config` resolves to an empty object, and
`useVariant("draft").has("header")` is `false`.

## Diagnostics

Nuxt Variants reports graph issues during Nuxt prepare:

- unknown parent variants
- circular inheritance chains
- unknown `app.config` override names
- structural `extends` values in `app.config`
- unknown fields in registry entries or runtime overrides

These are startup errors, not deferred warnings. One `VariantRegistryError`
contains every detected issue with a stable diagnostic code.

## DevTools Inspector

During development, Nuxt Variants adds a `Nuxt Variants` tab to Nuxt DevTools.
Use it to inspect:

- every registered variant
- direct `extends` relationships
- full parents-first resolution order and activity
- the application or Nuxt layer that declared each entry
- base registry config and `app.config` overrides
- resolved config after inheritance and merge priority
- filtering across names, parents, config keys, and source layers

Use the inspector's refresh action after changing `app.config`. Each request
resolves a new snapshot from the immutable build-time registry and Nuxt's
current app config instead of returning data captured when Nuxt started.

The inspector is development-only and does not register its server route in
production builds.
