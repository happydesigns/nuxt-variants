The local `0.3.0-next.1` preview adds `/core`, `/content` and `/devtools`
to `@happydesigns/nuxt-variants`. The published `0.2.0` package provides the
[Nuxt integration](/docs/getting-started) and [schema helpers](/docs/content-schemas).

## Build the local package

From the preview checkout, build the package once. The examples below can run
directly in that checkout using its package name.

```bash [Terminal]
pnpm install --frozen-lockfile
pnpm prepack
```

For a separate application, run `npm pack --ignore-scripts` after the build,
then install the resulting `happydesigns-nuxt-variants-0.3.0-next.1.tgz` by
its local file path in that application. The package installs Nuxt tooling
dependencies. Importing the core alone does not load Nuxt, Vue or the adapters.

## Portable core

A report can share a CSV delimiter with an audit export, while each chooses
its own columns. Save this module at the root of the checkout or in an
application that has the local tarball installed.

```js [variants.mjs]
import { createVariantResolver } from '@happydesigns/nuxt-variants/core'

export const variants = createVariantResolver({
  csv: { config: { delimiter: ',' } },
  summary: { extends: 'csv', config: { columns: ['id', 'total'] } },
  audit: { extends: 'summary', config: { columns: ['id', 'total', 'author'] } },
})
```

Resolve the name supplied by a record. An override applies to this call.
Run `node export-demo.mjs` to see the result.

```js [export-demo.mjs]
import { variants } from './variants.mjs'

const record = { variant: 'audit' }
if (!variants.isName(record.variant)) throw new Error('Unknown export variant')

const result = variants.resolve(record.variant, { csv: { config: { delimiter: ';' } } })
console.log(result.features)      // ['csv', 'summary', 'audit']
console.log(result.config)        // { delimiter: ';', columns: ['id', 'total', 'author'] }
```

Later parents contribute their complete inherited values. A variant's own
config takes precedence over its parents. Objects merge by field and arrays
are replaced as a unit. Deactivating a parent removes its contribution along
that branch. A disabled root resolves to `active: false` and empty config.

### Application defaults

An application can introduce fields in the resolver's second argument.
TypeScript uses these defaults when checking per-call overrides and the
resolved result. Inherited fields are optional because a parent can be disabled.

```ts [course.ts]
import { createVariantResolver } from '@happydesigns/nuxt-variants/core'

const courses = createVariantResolver(
  { progress: {}, course: ['progress'] },
  { progress: { config: { storagePrefix: 'course-progress' } } },
)
const reader = courses.resolve('course', { progress: { config: { storagePrefix: 'reader' } } })
if (reader.active) console.log(reader.config.storagePrefix) // 'reader'
```

Create one resolver per registry and rebuild it when the structure changes.
Use acyclic plain objects and arrays for config. The resolver can reuse the
default result for each name. Every call receives a fresh config copy, and
request-specific overrides are discarded after resolution.

## Comark Content

Install the Comark Content peer in the consuming application.

```bash [Terminal]
pnpm add 'comark-content@^0.6.2'
```

The example reads a Markdown document that selects the `audit` export defined above.

```md [content/weekly.md]
---
variant: audit
---

Weekly transaction export
```

```js [read-export.mjs]
import { comarkContent } from 'comark-content'
import fs from 'comark-content/sources/fs'
import { variantContent, variantField } from '@happydesigns/nuxt-variants/content'
import { variants } from './variants.mjs'

const reports = comarkContent('reports', {
  source: fs('./content', {
    cwd: import.meta.url,
    schema: { type: 'object', properties: { variant: variantField() } },
  }),
  plugins: [variantContent({ resolver: variants, defaultVariant: 'summary' })],
  onError: 'throw',
})

try {
  const file = await reports.get('/weekly')
  if (!file) throw new Error('Missing weekly export')
  const name = reports.variantName(file)
  console.log(reports.resolveVariant(name).features) // ['csv', 'summary', 'audit']
} finally {
  await reports.dispose()
}
```

Run `node read-export.mjs`. Parsing stores the selected name in
`file.meta.variant.name`. Resolution uses the current application's settings
even when the file was restored from a snapshot. Selection checks the
frontmatter field first, then stored metadata, then the configured default.

Use `field` to choose another top-level field and annotate that field with
`variantField()`. Content type generation can then emit literal names for
source data and query rows. The application owns validation of its other
fields and refinements. For Nuxt Content v3 collections, see the
[schema guide](/docs/content-schemas). Nuxt Content v4 compatibility still
needs verification against its adapter API.

### Limit a content source to a variant group

Define groups once alongside the resolver. Group names are chosen by the
application, and a variant can belong to multiple groups. The example limits
an editorial source to the article and event presets.

```ts
import { createVariantResolver, defineVariantGroups } from '@happydesigns/nuxt-variants/core'
import { variantContent, variantField } from '@happydesigns/nuxt-variants/content'

const resolver = createVariantResolver({
  header: {},
  article: { extends: 'header' },
  event: { extends: 'header' },
})
const groups = defineVariantGroups(resolver, {
  Editorial: ['article', 'event'],
  'With header': ['article', 'event', 'header'],
})

const field = variantField(groups.Editorial)
const plugin = variantContent({ resolver, allowedVariants: groups.Editorial })
```

Use `field` as `source.schema.properties.variant` and add `plugin` to the
source's `plugins` list. The field offers `article` and `event` as choices.
The plugin validates frontmatter when parsed and checks stored variant names
when selected from a snapshot. The generated document and query row types use
the same name union. A configured `defaultVariant` must also be in the group.

Pass the same `groups` to `createVariantDevtoolsData` for an optional group
filter and membership badges in the Inspector. The local comparison uses
**Editorial** for `article` and `event`, which also belong to **Content presets**.

### Limit Nuxt pages to a variant group

Use Nuxt's `PageMeta` augmentation to select a group for `definePageMeta`.
The example assumes that `variant-groups.ts` exports a `pagePresets` group.

```ts [types/page-variants.d.ts]
import type { variantGroups } from '../variant-groups'

declare module '#app' {
  interface PageMeta {
    variant?: (typeof variantGroups)['pagePresets'][number]
  }
}
```

The Playground binds `pagePresets`, which includes `article`, `event` and
`landing`. Its typecheck rejects `definePageMeta({ variant: 'hero' })` because
`hero` belongs to `features`. Select a group by its key in the declaration.
Pages can omit `variant`, and application code can still resolve registered
features with `useVariant`. Run `nuxt typecheck` to check the app's pages.

## DevFrame and Nuxt DevTools

Install the DevFrame peer in the development app alongside the preview package.

```bash [Terminal]
pnpm add -D 'devframe@^1.3.5'
```

Select the native Nuxt DevTools v4 dock in the module options.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@happydesigns/nuxt-variants'],
  variants: {
    registry: {
      csv: { config: { delimiter: ',' } },
      audit: { extends: 'csv' },
    },
    devtools: 'devframe',
  },
})
```

Open **Composable Variants** in Nuxt DevTools and select a variant from the
list or mobile menu. The links below the variant name jump to sections of the
detail view and mark the section in view. **Fields** shows the effective
value, contributing variant and source. Select an inherited field's source
variant to inspect its own configuration. Use **App overrides only** to show
fields supplied by app config. The link button next to a field copies an
inspector URL that selects the variant and that exact field. The recipient
needs access to the same inspector. Outside the Nuxt dock, the inspector
uses the host's snapshot. **Composition** always sits above **Fields**. The
arrows show the resolution order, with the selected variant highlighted at the
end. A standalone variant shows only its own name. The inspector distinguishes
direct parents from indirect ancestors when both contribute. Declared parents
excluded from resolution appear under **Parents not applied**.
In **Configuration**, **Resolved** shows the final result, including inherited
values. **Variant inputs** shows the selected variant's registry entry and app
overrides. The copy button copies the selected view.
Registry sources are shown when a Nuxt layer contributes a declaration.

### Standalone inspector

A Vite or Node development host can supply the same inspector with its own
snapshot. Reuse the resolver from `variants.mjs`.

```js [inspect.mjs]
import { createDevServer } from 'devframe/adapters/dev'
import { createVariantsDevframe, createVariantDevtoolsData } from '@happydesigns/nuxt-variants/devtools'
import { variants } from './variants.mjs'

const inspector = createVariantsDevframe({
  snapshot: () => createVariantDevtoolsData(
    { configKey: 'variants', registry: variants.registry, sources: {} },
    { csv: { config: { delimiter: ';' } } },
  ),
})
await createDevServer(inspector, {
  host: '127.0.0.1',
  mcp: false,
  openBrowser: '/__nuxt-variants/devtools/?transport=devframe',
})
```

Run `node inspect.mjs`. DevFrame opens the inspector with its authorization
link. The inspector reads a snapshot on demand. For offline use,
`createBuild(inspector, { outDir })` from `devframe/adapters/build` captures
the current snapshot and UI assets. Use **Refresh registry** in a live inspector
to fetch a new snapshot. In the native Nuxt dock the inspector also follows the
current tab's route and live app config automatically.

## Compare and verify

```bash [Preview checkout]
pnpm compare:prepare
pnpm compare
```

Open [the local comparison](http://127.0.0.1:4192/) and select **Veranstaltung**.
Compare its label in the published `0.2.0` UI and the preview. In the live
inspector, select `event` and find the `label` row under **Fields**. It shows
`Veranstaltung` and identifies the app config override on `event`. The
registry default under **Configuration → Variant inputs** is `Event`. The offline inspector
keeps the snapshot taken at startup.

Preparation builds the local package and downloads the integrity-checked
released inspector. The comparison uses the release tag's resolver code and
the same example inputs on both sides. Use `pnpm compare:presets ../ui` to
compare actual article and event data with typed presets when a
happydesigns UI checkout is available.

**Upgrade detail.** In a diamond where both parents inherit a base value,
the second parent's complete configuration takes precedence. In `0.2.0`,
the first parent's override could survive instead. Test such registries with
the application's own schemas, SSR and runtime overrides before migration.
