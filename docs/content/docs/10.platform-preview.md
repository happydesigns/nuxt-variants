The local `0.3.0-next.0` preview keeps the existing Nuxt module and adds optional
`/core`, `/content`, and `/devtools` entry points to the same package. There is
no separate package yet: the adapters share one resolver and release cycle,
and optional peers prevent Content and DevFrame from becoming Nuxt runtime
dependencies. Existing Nuxt contracts are checked against local revision
`626806d`; the interactive comparison uses the actual `v0.2.0` release.

## Implementation plan

This implements the approved platform direction in additive steps:

1. Expose an immutable, validated framework-neutral resolver that reuses the
   existing merge and feature semantics. Compile static lineages once; avoid
   caches of request overrides or resolved user config.
2. Add a Comark Content plugin for validated variant identity, semantic field
   types, and resolution against current overrides. Persist only identity,
   validate parsed snapshot identities when resolving, and keep domain schema
   refinements in application code. Existing Zod/Valibot schema behavior stays
   unchanged; content field composition is not config merging.
3. Add a portable read-only DevFrame definition and a modern Nuxt DevTools dock.
   Reuse the inspector UI, isolating transport and Nuxt route selection. Live
   queries read current state; offline builds capture an explicit snapshot.
4. Deliver a runnable old/new comparison with the same documents, registry,
   and overrides, plus package-consumer, browser, type, and performance checks.

Public module names, virtual aliases, schema helper contracts, and existing
resolution behavior remain compatible. New behavior is opt-in through the new
entry points. No package is published as part of this work.

## Choose the smallest integration

Use plain typed presets when the application has a few fixed page types. Use
the resolver when shared capabilities, multiple parents, active overrides, or
several consumers justify a graph. Add the Content plugin only when document
identity, validation, or generated content types need that same registry.

The current package keeps its existing Nuxt tooling dependencies. Importing
`/core` does not load Nuxt, Comark Content, Vue, or DevFrame, but installing this
package still installs its declared Nuxt dependencies. A separate package is
worth considering once actual non-Nuxt consumers justify a separate release
cycle and installation footprint.

## Portable core

```ts
import { createVariantResolver } from '@happydesigns/nuxt-variants/core'

export const variants = createVariantResolver({
  header: { config: { header: { title: 'Content' } } },
  toc: { config: { toc: { title: 'On this page' } } },
  article: { extends: ['header', 'toc'], config: { title: 'Article' } },
})

const result = variants.resolve('article', { toc: { active: false } })
if (result.active) {
  result.config.title.toUpperCase() // own required defaults remain required
  result.config.header?.title      // inherited values can disappear
}
```

Create the resolver once per registry. It copies and freezes the registry,
validates its graph, and compiles the static active lineages. Structure changes
require a new resolver. Each call validates only the supplied override entries,
reuses the static plan when possible, and resolves only the selected active
lineage when activation changes. Complete-parent merging preserves the Nuxt
module's diamond precedence and array replacement rules.

Returned config is copied so callers cannot modify another request's defaults
or override objects. There is no cache keyed by request config, document IDs,
or tenants. This deliberately trades a small copy cost for isolation. The
registry must use cloneable plain data objects and arrays without cycles; keep
functions, class instances and validators outside config. Schema/domain
validation remains separate.

The new core rejects unknown names; use `variants.isName(value)` at untyped
input boundaries. Known override fields retain inferred types. Additional
application config fields remain allowed, but need application-owned typing.

## Comark Content

Install the optional peer `comark-content@^0.6.2` only where needed:

```ts
import { comarkContent } from 'comark-content'
import fs from 'comark-content/sources/fs'
import { variantContent, variantField } from '@happydesigns/nuxt-variants/content'
import { variants } from './variants'

export const articles = comarkContent('articles', {
  source: {
    ...fs('./content/articles'),
    schema: {
      type: 'object',
      properties: { variant: variantField(), title: { type: 'string' } },
    },
  },
  plugins: [variantContent({ resolver: variants, defaultVariant: 'article' })],
})

const page = await articles.get('/welcome')
if (page) {
  const name = articles.variantName(page)
  const current = articles.resolveVariant(name, { toc: { active: false } })
}
```

The plugin stores only `meta.variant = { name }`. Selection priority is the
configured frontmatter field, existing parsed metadata, then the instance
default. `variantName()` validates again: parsed snapshots and `update()` do
not rerun `file:parsed`. Use `ingest()` when a constructed file still needs
transforms. Always resolve active features/config from the current resolver
and per-call overrides, never from a stored feature list.

Media files are left untouched. Metadata is therefore optional in Content's
general file type; use `variantName()` on documents to validate the identity.

`variantField()` marks the configured top-level field (default `variant`).
Its generated data and flattened query types narrow to the resolver's known
names. Use `{ field: 'pageVariant' }` to select another top-level field. Nested
variant selectors and several independently configured selectors in one
instance are outside this preview's contract. One plugin owns selection per
Content instance.

Generate content types from the source with its explicit schema. A parsed
snapshot alone stores documents, not the source's semantic field declaration;
carry the source schema explicitly if generating types from snapshots.

Comark Content 0.6.2 exposes a small JSON Schema subset. This extension does
not implement general JSON Schema validation or replace Zod/Valibot domain
schemas and cross-field refinements. Existing `/schemas` behavior is unchanged:
schema field composition and complete-parent config resolution remain distinct
policies. Pass the final shared registry to both integrations; the plugin does
not discover Nuxt layer additions automatically.

Nuxt Content v4 is an upstream integration target, not a verified compatibility
claim. Its final wrapper API still needs its own adapter acceptance.

## DevFrame and Nuxt DevTools

Install the optional `devframe@^1.3.5` peer for portable development tools:

```ts
import { createVariantsDevframe, createVariantDevtoolsData } from '@happydesigns/nuxt-variants/devtools'
import { createDevServer } from 'devframe/adapters/dev'
import { variants } from './variants'

const definition = createVariantsDevframe({
  snapshot: () => createVariantDevtoolsData({
    configKey: 'variants', registry: variants.registry, sources: {},
  }, {}),
})
await createDevServer(definition, { host: '127.0.0.1', mcp: false })
```

The single `nuxt-variants:get-snapshot` query reads current state without
permanent RPC caching. `snapshot: true` also allows `createBuild()` from
`devframe/adapters/build` to bake an offline snapshot using the same definition.
The plugin declares no mutation methods, watchers, agent tools, or services.
Hosts own auth, transport lifecycle, and disposal. Their built-in RPCs are
separate from the Variants namespace.

The client discovers a same-origin `__connection.json`. Explicit
`?transport=devframe` fails visibly when it is absent; `?transport=legacy` uses
the JSON endpoint. Connection failures stay errors and are not silently
presented as empty registries. Refresh is user-triggered, with no polling.
Closing the view disposes its RPC connection. In the Nuxt dock, a same-origin
DevFrame in-page channel reads the current route variant and only the variant
app-config section. Change events update the view without polling. This
development-only channel has a read query and notifications, no navigation or
config-write actions. It is disposed on view/app teardown or hot replacement.
Browser context stays in that page's channel rather than a shared Node
"current route" or override cache, keeping separate tabs independent.
The legacy iframe bridge remains separate; standalone and offline viewers do
not attempt to connect to a Nuxt page.

For Nuxt DevTools v4, opt in without changing the legacy default:

```ts
export default defineNuxtConfig({
  modules: ['@happydesigns/nuxt-variants'],
  variants: { registry, devtools: 'devframe' },
})
```

This registers a native iframe dock and the read-only query using the
`devtools:ready` context. The existing JSON endpoint remains available for
comparison. Production builds register neither inspector routes nor metadata.

The inspector SPA uses Nuxt UI 4.10 primitives and semantic theme tokens,
with its own domain layout and JSON visualization. Nuxt UI and Lucide are
build-time dependencies only. Fonts are local system fonts and the used icons
are bundled, allowing the same UI to work offline.

## Compare and verify

Run `pnpm compare:prepare`, then `pnpm compare` and open `http://127.0.0.1:4192/`.
The command serves only loopback addresses, uses artificial article/snippet/
course documents, and reads the real resolver code from the local `v0.2.0`
Git tag. Both sides use the same registry and current overrides. The preview
loads a real parsed Content snapshot. The offline inspector captures startup
state and intentionally does not follow later toggles. Stop both servers with
Ctrl+C. Set `VARIANTS_COMPARE_PORT` to use another adjacent port pair.

Preparation builds the preview and downloads the published 0.2.0 inspector,
checking its npm SHA-512 integrity. The legacy inspector therefore uses the
actual old UI; the new live/offline inspector uses Nuxt UI. Once prepared, the
comparison runs locally without fetching frontend assets from external services.

Run `pnpm bench` to compare the current Nuxt compiled-plan path with the new
portable path, including output isolation. Faster execution is not a migration
requirement or an assumed benefit; compare relative costs on the same machine.
Package import isolation, equivalent behavior, fewer integration-specific
definitions, and useful live/offline diagnostics are the relevant benefits.

Before changing a productive consumer, verify collection schemas, generated
types, SSR, current route selection, and runtime overrides in that application.
Resolution shadow tests do not replace those application checks.
