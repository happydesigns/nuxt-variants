## Feature Variants And Collection Variants

Real projects usually split variants into small feature names and larger
collection names.

```ts [nuxt.config.ts]
registry: {
  dates: { config: {} },
  authors: { config: {} },
  category: { config: {} },
  header: { config: {} },
  toc: { config: {} },
  article: {
    extends: ["dates", "authors", "category", "header", "toc"],
    config: {},
  },
  event: {
    extends: ["dates", "category", "header"],
    config: {},
  },
}
```

## Feature-Gated Layout

Use `has()` for inherited feature presence instead of checking config keys
directly.

```vue [layouts/article.vue]
<script setup lang="ts">
const collection = "article";
const { config, has } = useVariant(collection);
const hasHeader = has("header");
const hasToc = has("toc");
</script>

<template>
  <ArticleHeader v-if="hasHeader" :config="config" />
  <ArticleToc v-if="hasToc" :config="config" />
  <ContentRenderer />
</template>
```

## Application Override

Use `app.config.ts` to tune a variant without changing the build-time default.

```ts [app.config.ts]
export default defineAppConfig({
  variants: {
    article: {
      config: {
        backButton: { label: "All articles" },
        list: { limit: 12 },
      },
    },
  },
});
```

## Owner-Editable Settings With Nuxt Studio

Current Nuxt Studio versions provide schema forms for Nuxt Content data, not
for `app.config.ts`. Keep the variant graph in code and expose only intentional
owner-editable fields through an app-owned data collection.

```ts [content.config.ts]
import { defineCollection, defineContentConfig } from "@nuxt/content";
import { z } from "zod";

export default defineContentConfig({
  collections: {
    settings: defineCollection({
      type: "data",
      source: "settings/*.yaml",
      schema: z.object({
        copyButton: z.object({
          label: z.string().min(1),
          successLabel: z.string().min(1),
        }),
      }),
    }),
  },
});
```

Map that validated data into Nuxt's reactive app config once at application
startup:

```ts [app/plugins/content-settings.ts]
export default defineNuxtPlugin(async () => {
  const { data: settings } = await useAsyncData("site-settings", () =>
    queryCollection("settings").first(),
  );

  watchEffect(() => {
    if (!settings.value) return;

    updateAppConfig({
      variants: {
        copyButton: {
          config: { copyButton: settings.value.copyButton },
        },
      },
    });
  });
});
```

The collection schema is the editor-facing contract. Do not mirror the entire
variant registry into content: inheritance and developer-owned defaults remain
code, while site owners see only the fields they are expected to change.

## Related UI Slot Overrides

Nuxt Variants handles semantic config and schema composition. Slot class
composition is a separate concern that belongs in Nuxt UI, component props, or
utilities such as `tailwind-variants`.
